# Компилятор 2D-грамматики

Пакет `vstuxls.grammar2d.compiler` — «lex/yacc для таблиц»: он читает ту же YAML-грамматику, что и
старый матчер (`vstuxls.grammar2d`), но не просто выполняет её, а **анализирует**, находит противоречия
и неточности и умеет выполнять сам (новый движок с планировщиком). Формальный смысл грамматики —
в [grammar_semantics.md](grammar_semantics.md).

```
YAML (v1/v2) ─► frontend ─► IR ─► lint ─► geometry (STN) ─► celltypes (регулярки) ─► ambiguity/policy
                                              │
                                              └──► planner ─► engine ─► selection (глобальный выбор)
                                                                  ▲
                                          fuzz (таблицы из грамматики) ┘   diff (сверка со старым матчером)
```

## Запуск

```
uv run vstuxls-grammar check   cnf/grammar_root.yml [--json] [--strict] [--min-severity warning]
                                                     [--no-geometry] [--no-lexical] [--no-ambiguity]
uv run vstuxls-grammar explain cnf/grammar_root.yml frame_based_lesson   # вычисленные размеры, окна, порядок join
uv run vstuxls-grammar policies cnf/grammar_root.yml                     # политика выбора (priority/prefer/overlap) по паттернам
uv run vstuxls-grammar match   cnf/grammar_root.yml table.xlsx [--all]   # новый движок на таблице
uv run vstuxls-grammar diff    cnf/grammar_root.yml table.xlsx           # сверка нового движка со старым матчером
uv run vstuxls-grammar fuzz    cnf/grammar_root.yml [--pattern P] [--count N] [--seed S]
```

Команда `vstuxls-grammar` доступна после установки пакета. Из исходников (Windows `cmd`):
`set PYTHONPATH=src && uv run python -m vstuxls.grammar2d.compiler <команда> ...`.
Код возврата `check`: 1 при ошибках (или при предупреждениях с `--strict`).

Из Python:

```python
from vstuxls.grammar2d.compiler import compile_grammar
from vstuxls.grammar2d.compiler.engine import Engine

result = compile_grammar('cnf/grammar_root.yml')   # result.ir, result.report
print(result.report.format())
roots = Engine(result.ir).run(grid).roots           # grid — ExcelGrid / TxtGrid
```

## Что проверяется

Каждая диагностика имеет код, положение в YAML (файл:строка), подсказку и, где возможно, **свидетеля** —
конкретный контрпример.

| Этап | Коды | Что ловит |
|------|------|-----------|
| Структура (`lint.py`) | G001–G020 | неизвестный `kind`/ключ (с подсказкой «возможно, имелось в виду…»), битые ссылки, циклы зависимостей и `extends`, недостижимые и непродуктивные паттерны, неиспользуемые типы ячеек, корень, шаблоны, импорт; `G020` — v1-трактовка `size` компонента |
| Геометрия (`geometry.py`, `stn.py`) | GEO001–GEO006 | `location/size/gap/relations` переводятся в два STN (оси x и y); отрицательный цикл = **противоречие** (свидетель — цепочка ограничений и сумма < 0); замыкание даёт неявные границы и избыточные ограничения; вычисленный размер паттерна |
| Лексика (`celltypes.py`) | LEX001–LEX005 | регулярки `cell_types` порождают строки-свидетели; общая строка у двух типов = `LEX001`; недостижимый паттерн типа = `LEX003`; пример, не узнаваемый своим типом = `LEX005`. Вместо ручных lookahead — `priority`/`except` у типа |
| Неоднозначность (`ambiguity.py`) | AMB001, AMB002, POL001–POL005 | альтернативы (`alt`/`general`/`extends`), способные совпасть на одном месте без правила выбора; отключённая фильтрация накладок; отрицательные веса вместо `forbid`; циклы `prefer` |

Анализ геометрии — это **корректная релаксация** (если STN противоречива, паттерн действительно не может
совпасть; обратное неверно: для `bbox`/`min`/`max` ограничения не моделируются точно). Анализ регулярок —
по выборке, поэтому отсутствие `LEX001` не доказательство.

## Новый движок (`engine.py`)

* Планировщик (`planner.py`): из замыкания STN для каждого ребра ещё не найденного компонента выводится
  **окно** допустимых значений при уже найденных соседях; порядок join выбирается жадно (самый редкий
  компонент первым), кандидаты берутся из индекса по рёбрам (`bisect`), а не перебором. Вместо ручных
  «опорных линий» грамматики порядок проверок определяется геометрией.
* Нет жадного отсечения: сначала собираются *все* допустимые разборы (до `max_parses_per_box` на рамку),
  политика (`priority`, `prefer`, `overlap`, `confidence`) применяется отдельным слоем — `selection.py`.
* На корпусе `tests/test_data/` корни совпадают со старым матчером (`diff`); на `ФЭВТ 3 курс 2026 mini.xlsx`
  — 11 с у старого матчера и 0.5 с у нового.

### Осознанные отличия от старого матчера (`diff` их показывает)

1. Новый движок **полнее**: не отбрасывает кандидатов эвристикой «пересекающихся совпадений своего паттерна»,
   поэтому находит больше альтернатив (например, `discipline_with_several_groups` 13 против 4, пары «занятие на
   несколько групп»). Выбор между ними выполняется глобально по политике.
2. Рамка родителя может быть шире охвата внутренних компонентов, если её однозначно задаёт контекст
   (`padding-top: 0` к внешнему `hour_range` + фиксированный `size`).
3. `size` у терминала (`kind: cell`) в режиме v1 не проверяется (так было у старого матчера), в v2 и при
   `Engine(strict_cell_size=True)` — проверяется.
4. Массивы: `fill` собирает связные кластеры непересекающихся элементов; `allow_breakdown` режет слишком
   крупный кластер на блоки максимального `size`. Старый матчер дробил иначе, поэтому число найденных
   под-массивов отличается (корни при этом совпадают).
5. На один корень (`count_in_document`) остаётся лучший разбор; несколько разборов одной рамки схлопываются.

## Диалект v2 (`grammar: 2`)

Старые грамматики работают без изменений. Для v2 добавлено:

| Возможность | Пример |
|-------------|--------|
| **alt** — выбор из нескольких паттернов | `kind: alt`, `one_of: [field_text, field_number]` |
| **require / forbid** — предикаты контекста | `forbid: {glued_caption: {pattern: caption, location: {margin-left: 0}}}` (вместо `weight: -10`) |
| **relations** — отношения между рёбрами | `caption.top == value.top`, `value.left - caption.right in 0..1`, `title.bottom <= body.top` |
| **count** — квантор у компонента | `remark: {pattern: note, count: 0..2}` → компоненты `remark`, `remark_2` (необязательные), порядок сохраняется |
| **align** в массивах | `align: both \| start \| end \| none` (в v1 неявно `both`) |
| **templates** — шаблоны/параметры | `templates: {field: {name: 'field_${kind}', params: {kind: [text, number]}, body: {...}}}`; в `${}` — безопасная арифметика |
| **policies** — политика отдельно от структуры | `policies: {field_number: {confidence: 0.95, priority: 1, prefer: [...]}}` |
| **import** | `import: [common_cell_types.yml]` (вместе с `include_grammars` из v1; повторный импорт — `G018`) |
| `size` у компонента — это размер самого компонента | в v1 он (по историческим причинам) ограничивал размер родителя — компилятор переносит его с предупреждением `G020` |
| Необязательные внутренние компоненты расширяют рамку родителя | в v1 — нет (совместимость) |

Рабочий пример — `tests/test_data/v2_demo_grammar.yml` (заголовок и столбец полей «Подпись: значение»).
Для него `check` не даёт замечаний, `fuzz` порождает таблицы, а движок находит их целиком.

## Fuzz: таблицы из грамматики

`fuzz` порождает таблицу «из грамматики»: размещает компоненты области в окнах STN, подбирает тексты по
регуляркам типов ячеек (проверяя настоящим `CellClassifier`), строит массивы и объединённые ячейки; затем
прогоняет движок и сверяет найденные рамки с ожидаемыми. Расхождение означает либо ошибку движка, либо
дефект грамматики (регулярка, которую классификатор относит к другому типу; неоднозначная вложенность
массивов). Контекстные (`outer`) ячейки, общие для соседей, сливаются в одну. Если структура слишком
сложная (например, `weeks_calendar`), генератор честно сообщает причины неудач — это инструмент
самопроверки, а не доказательство полноты.

## Модули

| Модуль | Роль |
|--------|------|
| `source.py`, `diagnostics.py` | YAML с позициями строк, диагностики и коды |
| `frontend.py`, `templates.py` | YAML (v1/v2) → IR; шаблоны, count, relations |
| `ir.py` | IR: `PatternIR`, `ComponentIR`, `LocationIR`, `PolicyIR`, `GrammarIR` |
| `lint.py` | структурные проверки |
| `stn.py`, `geometry.py` | STN (Беллман–Форд, Флойд–Уоршелл), анализ размеров и расположения |
| `celltypes.py` | анализ регулярок типов ячеек |
| `ambiguity.py` | неоднозначность альтернатив и политика |
| `planner.py`, `engine.py`, `selection.py` | планировщик, матчер, глобальный выбор |
| `diff.py` | сверка со старым матчером |
| `fuzz.py` | генератор тестовых таблиц |
| `cli.py`, `__main__.py` | командная строка |
